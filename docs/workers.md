# Resident MLX workers

The existing application can run 1, 2, or 4 independent resident MLX processes. `mlx.prefillSize` can be set separately from decode `batchSize`; it defaults to the decode capacity for backward compatibility. See `docs/batching-report.md` for the measured one-model continuous batching candidate. Each process loads the local Qwen 2.5 3B base and the same accepted role adapter, has independent attention/generation state, a bounded input queue, and a continuous batch generator. It does not share attention state or model objects between processes.

`mlx.workers` selects the process count. If omitted, the CLI applies all measured settings from `config/residency.json` (currently two workers, batch 16, concurrency 32). Explicit worker settings override this default. The CLI writes a unique effective configuration snapshot before launch, so the sandboxed application uses the same configuration as the worker supervisor. `mlx.batchSize` is the maximum in-flight batch per worker (1..64). Set application `concurrency` up to `workers * batchSize`. A shared scheduler assigns work to available slots immediately, preferring workers with fewer active requests. Queues and leases are bounded; completed requests return slots independently, without a round-robin barrier. All database and result writes remain in one application process. SQLite FULL/WAL transactions and durable output receipts retain the existing checkpoint recovery behavior.

The descriptor supervisor starts the workers before applying the application's sandbox. Workers keep their stricter read-only model/runtime sandbox. The application denies all networking and input writes. Pipe sockets use the event loop, avoiding blocking filesystem-thread-pool starvation with multiple workers. No hosted inference or network fallback exists.

The aggregate budget is **32,000,000,000 bytes**, with 1 GB reserved from MLX allocations for the application, supervisor, and overhead. Four-worker settings are in `config/workers-4.json`: 7,750,000,000 bytes per worker, batch 16, application concurrency 64. The supervisor samples physical footprint of itself, application, and all workers every 250 ms; exceeding the budget terminates the run and preserves checkpoints. MLX allocation limits are set before model initialization. Sampling is not a hard aggregate kernel allocation limit; a sub-250ms transient can precede termination. Per-worker MLX limits provide the allocation bound.

Run the identical synthetic comparison from the project root:

```sh
node pipeline/benchmark.ts matrix
```

The benchmark creates only synthetic fixtures under project `state/`, runs 192 identical held-out files with 1, 2, and 4 workers, uses three measurement windows, and compares every output field against an exact expected result. Each configuration gets its own state/output directory. It reports completed files/minute, generated tokens/second including initialization and persistence, MLX allocation peaks, aggregate physical footprint/resident memory, and Apple GPU device utilization. GPU telemetry is system-wide and may include other applications. Reports include all samples and failed configurations; no missing or invalid output qualifies as stable. Runs shorter than 60 seconds do not qualify for selection. The fastest passing configuration is written to `config/residency.json` with its evidence path.

These performance fixtures use the existing narrow synthetic learned adapter. They measure real Qwen/MLX execution and pipeline correctness, but do not establish comprehensive production semantic-role acceptance. The production CLI continues requiring accepted role manifests; this change does not bypass that requirement. The settings files are parameter bundles: set `concurrency` at the root of a run configuration and set `workers`, `batchSize`, `memoryBytes`, and `budgetBytes` inside `mlx`. Preserve the existing base/runtime/adapter paths and analysis token limit. Use the existing `node pipeline/cli.ts run /absolute/config.json` entrypoint only when production execution is separately authorized.

Restart the same production command and work path to recover interruption. Completed outputs with matching identities and hashes are reused. In-flight attempts are marked interrupted and leased again. A dead worker aborts the current run; the supervisor cleans up all resident processes. Restart creates a fresh pool and retains the centralized checkpoint.
