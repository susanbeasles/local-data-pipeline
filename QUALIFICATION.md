# Guest backend qualification

Run `node pipeline/qualification.ts /absolute/nonsecret-config.json` only after the operator has separately verified an already-running, dedicated VM has the private network boundary, no host mounts, and spare shared memory. The command never boots a VM, downloads assets, installs software or executes an inference probe on the host. Config contains `mac` (the existing macOS Guest config), guest `python` absolute path, and `runtime`/`model` objects with guest absolute `root` and lowercase SHA-256 `sha256`. Runtime and model directories must be separate, canonical and contain regular files only; the digests use pipeline/seal.ts's no-symlink convention. Runtime Python and MLX modules must reside under the pinned runtime root.

A successful synthetic-backend receipt requires a fresh guest challenge, Darwin arm64, matching runtime/model tree digests before and after inference, an MLX version, available Metal, GPU arithmetic evaluating to 14, and nonempty generation from a fixed synthetic prompt with eight generated tokens maximum. It proves this narrow backend probe; it does not attest VM network/host-file isolation, metadata isolation, workload quality, or full pipeline readiness. Do not use it to automatically upgrade provisioning receipts. Errors produce no success receipt. Guest.execute currently imposes a 120-second total bound; hashing/loading a large model may therefore fail closed on timeout.

## Verified command transport

Installed Tart 2.41.0 `exec --help`, queried with a separate temporary HOME/TART_HOME and telemetry/pruning disabled, advertises `tart exec [-i] [-t] <name> <command> ...`. The existing `Guest.execute` argv form is supported. Execution requires the Tart Guest Agent running inside the guest; presence in the configured pinned base image remains unverified. Tart's `-i` flag attaches host stdin. Existing bootstrap uses a bounded nonsecret `--config-base64` argument and therefore does not require stdin transport. No actual guest command was executed. A host process cannot directly open a guest-kernel PostgreSQL Unix socket; runtime SQL transport must execute inside the guest or use a separately verified guest command protocol. This qualification command does not supply that SQL transport.

## Native platform guest binding

Studio accepts `platform: {config: "/guest/operator/platform.json", guest: {mac, node: {path, sha256}, entry: {path, sha256}}}`. `mac` is the existing validated local Tart configuration. Node and entry paths are absolute guest files with SHA-256 pins; the guest must already have its Guest Agent, Node runtime, frozen entry and imports installed, and its local PostgreSQL configured. The entry implements the platform.ts single-request JSON stdin/stdout protocol. Freeze and protect the complete runtime/import closure; pinning entry alone does not attest mutable imports or configuration.

The bridge verifies Node and entry digests through the guest agent before and after each call, then exchanges at most 2 MiB of JSON over `tart exec -i`. Requests stay on stdin; they are never command arguments or logged diagnostics. The existing native action allowlist applies before any guest call, including rejection of `work`. Commands use absolute argv, no shell, and no SSH or TCP transport. Guest failures do not fall back to host PostgreSQL. The bridge neither boots nor provisions VMs. Configure the guest SQL listener as a guest-local Unix socket; do not use host paths for that socket. Configuration ownership and VM isolation remain operator prerequisites.
